# kb-build — 生成知识库

at2s 的子流程，不对外暴露。**调用时机**：用户要求为某张表或某批表建知识库；kb-check 报出"待补充"或"潜在可添加"并给出建议后，跟从该建议。

## 产出

- `.knowledge/architecture/<表名>.md` —— 表自身描述，含字段级介绍
- `.knowledge/architecture/correlation.md` —— 表 × 表 join 矩阵 + 关系明细 + 跳表注意事项

## 流程

### 1 抽样认识

调 2 号（db-access）对目标表抽样（默认 ≤100 行）；码值类字段额外看去重取值，不受行数上限。

抽不到数据就报告并停下，**不要凭表名猜着写知识库**。

### 2 收集用户信息

四种情形，按实际情况走：

- 用户在对话里直接给
- 读取用户指定的文件
- 批量文件（一份文件含多张表的信息）→ 一次处理多表
- **用户不提供任何额外信息** → 纯数据驱动，只靠抽样行与字段名推断

### 3 生成自身描述

写入 `architecture/<表名>.md`。**每个字段的介绍都标注来源**：`用户提供` 或 `数据推测`，后者是 6 号复查的重点对象。

目标文件已存在时，先摘要其现状，再询问追加 / 重写 / 跳过，**默认跳过，禁止静默覆盖**。

格式固定（kb-check 依赖）：文件名与表名一致；`## 表描述` 与 `## 字段` 两节。

### 4 推断关系

**批量时先把本批所有表的第 3 步做完，再统一做第 4 步。** 否则先处理的表看不到后处理的表，关系会缺一半且结果依赖处理顺序。

- 推断依据：① 字段名相同或高度相似 ② 用抽样的示例值形态交叉验证（取值格式、长度、值域是否一致）
- 推断范围：已入库的表 + 本批次新建的表
- 关系是推测，一律先标 `推测`，经用户确认后才改 `已确认`

## correlation.md 结构

三节。

### 一、join 矩阵

行列都是表名，单元格填这两张表推测可 join 的字段：

| | ads_cust_info_d | dws_cust_aset_d | dim_product |
|---|---|---|---|
| ads_cust_info_d | — | pty_id | |
| dws_cust_aset_d | ↖ | — | |
| dim_product | ↖ | ↖ | — |

- 只填**上三角**，下三角一律 `↖`，对角线 `—`。矩阵对称，两边都填就是重复维护
- 多个可 join 字段用逗号分隔，如 `pty_id, data_dt`
- 尚未分析或关系未定则**留空**
- 已确证与某表无关系（有充分证据，或用户明确说明）则填 **`∅`**，区别于“还没分析”的留空

**孤立表**：某些表天然无法与他表 join（如只有一行、专为笛卡尔积而存在的参数表）。
一旦确证某表与所有现存表都无关系，将它的整行整列（除对角线）填 `∅`——
这样 kb-check 会归入“孤立”而非“待补充”，不再反复提示。

判断：**整行整列（除对角线）全为空 = 待补充；全为 `∅` = 已确认孤立。**

### 二、关系明细

逐条列出：表对 / join 字段 / 推断依据 / 状态（`推测` 或 `已确认`）。

状态只放在这里，不要塞进矩阵格子，否则格子宽度失控。

### 三、注意事项

除描述与关系之外，生成过程中发现的**跳表或跳字段的注意事项**也记在本节，按条目记录。
每条包含两部分：**注意事项本身** + **涉及的表**。

| 注意事项 | 涉及的表 |
|---|---|
| <一句说清坑在哪、应该怎么写> | <表A>、<表B> |

典型来源：字段存储类型带来的比较方式、码值表的关联附加条件、金额字段能否直接汇总、
各表时间覆盖不一致、粒度差异导致的重复计数等。

写入要求：

- 一条只讲一事，写成可直接执行的结论，不是现象描述。
- 只记**跳表或影响写法**的事；单表内部的字段细节写在 `<表名>.md` 里。
- 5 号（text2sql）**每次生成 SQL 前都会通读本节**，因此此处的条目相当于硬约束，宁缺勿滥。

## 幂等

- `<表名>.md` 已存在 → 走第 3 步的询问，不覆盖
- 矩阵中已有该表的行列 → **整行整列重写**，不追加新行
- 关系明细按表对查重，表对按字典序归一（`A×B` 与 `B×A` 视为同一条），命中则更新该条
- 新增一张表 = 矩阵加一行一列；不删除既有内容

重复执行任意次数，产出一致。
