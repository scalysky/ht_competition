# kb-modify — 修改知识库

at2s 的子流程，不对外暴露。**调用时机**：用户要解答 3 号（kb-build）生成时留下的困惑；用户手动指出知识库有错。

## 两种模式

用户未指明时，**先问进入哪种模式**，再往下走。

### 模式 A：复核未确认内容

知识库里未经用户拍板的内容分**两类**，来源与置信度不同，分开收集：

- **困惑**：各 `<表名>.md` 的 `## 待确认` 段里的条目——agent 没把握、明确需用户定夺。
- **推测**：“大概率是、但未经用户确认”的内容——具体为各 `<表名>.md` 字段表中来源为 `数据推测` 的行，以及 `correlation.md` 关系明细中状态为 `推测` 的条目。

流程：

1. 用户可指定只看哪一类（如“有哪些推测的内容”即只收推测）；未指定则两类都收集，分开列出。
2. 两类均为空则告知“无待确认困惑、无未确认推测”，结束。
3. 与用户逐项沟通，取得每项结论。

### 模式 B：用户指错

1. 先问：**要改进哪些数据表的知识？**
2. 依次总结这些表的现有知识（表描述 + 字段 + 相关关系），逐表呈现给用户。
3. 与用户沟通，定位错在哪、应改成什么。

## 修改计划（两模式共用）

沟通完成后、动手前，先与用户**约定修改计划**：逐条列出

- 要改哪个文件（`<表名>.md` / `correlation.md`）
- 改哪一处、改成什么
- 该结论的来源（`用户确认`）

用户确认计划后才写。计划外的内容一律不动。

## 写入规则

- 确认的口径/含义 → 写入对应字段或表描述，**来源标 `用户确认`**（高于 `表描述`、`数据推测`）。
- 该条若来自某表的 `## 待确认`，落库后**从 `## 待确认` 中移除**，避免下次重复收集。
- 纠正字段/表描述错误：直接改正文，并在该条后注明依据（用户说明）。
- 涉及表间关系：改 `correlation.md`——修正 join 字段、或把关系明细的状态从 `推测` 升为 `已确认`；确证无关系则按孤立规则填 `∅`。
- **绝不删除未提及的内容**；只动计划里约定的部分。

## 幂等

- 已解决并移出 `## 待确认` 的困惑，重跑模式 A 不会再出现。
- 同一处结论重复写入时，覆盖为一致结果，不追加重复条目。
- 未确认的困惑保留原样，不擅自替用户下结论。
