# kb-refine — 完善知识库

at2s 的子流程，不对外暴露。**调用时机**：text2sql 在 troubleshooting 里积累了疑问或错误后，据此回头完善知识库；用户要求消化这些记录。

与 kb-modify（4 号）的分工：4 号处理**知识库内部**的未确认内容与用户当面指错；本流程消化 **text2sql 用过之后留下的** troubleshooting 记录，重点是把导致出错的黑话、别名沉淀进知识库。

## 触发与配置

读本目录下的 `config.md` 决定触发方式。**该文件不存在或未开启即为默认：手动**——只在用户明确要求时消化。

配置项（用户可改）：

- `mode`：`manual`（默认）/ `auto`
- `auto` 时的触发阈值，任一满足即触发：`每 N 小时` / `每天 HH:MM` / `每积累 N 条未消化记录`
- `last_run`：上次消化时间戳，由本流程写回

**关于"自动"的现实**：skill 无常驻进程，不能自行定时。时间类阈值需外部调度器（如 cron）周期性唤起 at2s；被唤起时本流程才读 config、比对 `last_run` 与未消化条数，判断是否到点。条数类阈值可在 text2sql 每次追加记录后顺带检查。

**自动模式的边界**：`auto` 只自动应用 troubleshooting 中**已带明确答案**的条目（`用户解答：…` 或错误记录里已给 `正确写法`）。需要现场判断、答案缺失的条目一律留待手动，不在自动模式下替用户下结论。

## 输入

- `.knowledge/troubleshooting/questions.md` —— 5 号遇到的模糊点及处置
- `.knowledge/troubleshooting/errors.md` —— 用户反馈的 SQL 错误

无未消化条目则告知用户"暂无待完善项"，结束。

## 流程

1. 读两个文件，列出**未消化**条目。
2. 逐条判定根因，归到下面「分流」之一。
3. 与用户约定修改计划（改哪个文件、改什么），确认后才写；计划外不动。**手动模式必须走这一步**；自动模式跳过约定，直接应用已带明确答案的条目（见「触发与配置」的自动边界）。
4. 写完后在 troubleshooting 对应条目标注 `已消化`，不删除原记录（留作历史）。

## 分流

| 根因 | 写入 |
|---|---|
| 单个表的字段含义 / 口径错 | `architecture/<表名>.md`，来源标 `用户确认` |
| 表间关系错（join 字段、方向、该不该关联） | `architecture/correlation.md`（矩阵 / 关系明细 / 注意事项相应处） |
| 用户用了缩写、黑话、别名导致理解错 | `conventions/aliases.md` **一份**，且对应 `architecture/<表名>.md` 里**再记一份** |

## 黑话别名的双写

黑话、别名是最易复发的错误源，**有意冗余存两处**：

- `conventions/aliases.md`：全局字典，逐条记 `口语/黑话 → 库内准确值或字段`，附涉及的表。这是跨表检索的总入口。
- `architecture/<表名>.md`：在该表下加 `## 别名与黑话` 节，只记与本表相关的条目。生成 SQL 通读某表知识时能就近看到。

两处内容允许重复，但同一别名在各自文件内不重复；已存在则更新那一条。

## 幂等

- 已标 `已消化` 的 troubleshooting 条目，重跑不再处理。
- 同一别名 / 同一处结论重复写入时覆盖为一致结果，不追加重复条目。
- 未与用户确认的条目保留原样，不擅自下结论。
